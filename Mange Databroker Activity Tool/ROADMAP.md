# Project scope and plain-English roadmap

This document records the intended direction and work sequence for the
Databroker Management Tool. It is a planning document, not
implementation. The project owner will clarify details as development
approaches them. Do not fill in classes, functions, variables, storage
schemas, or inter-module orchestration based only on this document.

The intended repository outcome is an unfinished but understandable,
modular boilerplate for public GitHub: other people should be able to inspect,
fork, and adapt it for their own projects. Clearly label implemented
capabilities, incomplete scaffolding, and future plans. The repository uses
the MIT license; publishing the repository does not itself grant permission
beyond the terms of that license.

## Purpose

Help ordinary citizens learn which commercial data brokers may hold or use
their personal information, keep a reliable record of what happened, and
prepare fact-based material and questions for a professional attorney.

The user should be able to keep evidence and events organized over time.
Separate user-provided evidence from machine-created summaries, analysis, and
research. The agent may help research and reason about possible impacts and
recourse, but its explanations are preliminary and must be presented so a user
and attorney can inspect the underlying facts and sources.

## Agreed scope and boundaries

- **Primary user:** An ordinary citizen seeking to understand their rights and
  organize a possible data-broker case.
- **Legal context:** Global in intended scope, with actual source and legal
  coverage developed jurisdiction by jurisdiction. Do not imply that all
  jurisdictions or laws have been researched.
- **Primary subject:** Commercial data brokers across sectors and jurisdictions,
  including identity, advertising, financial, health-related, business, and
  other personal-data markets. An organization is not a broker merely because
  it holds personal data; assess the activity against the relevant source and
  jurisdiction. The project does not audit institutions as a whole.
- **Research:** Use publicly accessible sources. Search queries must not
  contain personal identifiers. Do not break laws or submit private personal
  information to search engines, research sites, or brokers as part of
  research. The research subject is the broker and its public record, not the
  victim's personal data.
- **Incomplete broker visibility:** Public registries, directories, and this
  project's curated list are not comprehensive. A broker not found in sources
  checked must be described as "not found in the sources checked," never as
  nonexistent or cleared. Treat lack of public listing or transparency as a
  risk signal that warrants further lawful research. The project may treat
  hidden or unlisted brokers as a higher-priority risk hypothesis, but must
  not state that they are statistically more likely to engage in misconduct
  unless credible evidence establishes that comparison. Unlisted status alone
  is not proof of unlawful or illicit conduct.
- **Model runtime:** Use local Ollama as the intended model runtime. A local
  model does not automatically make every part of a product private; later
  design must account for local files, logs, backups, model downloads, and any
  future network connections.
- **Development records:** Case material is intended to be stored locally by
  the application, not in a browser or cloud service. Production encryption
  and deployment requirements are future decisions.
- **Evidence integrity:** Preserve original user-provided material distinctly
  from OCR text, extracted text, annotations, summaries, and agent analysis.
  Make it possible to tell what came from the user, what came from a source,
  and what was generated by the agent.
- **No automatic legal conclusion:** The agent may explain possible issues,
  rules, impacts, and administrative options for counseling and preparation.
  It must show its basis, uncertainties, and source material so a professional
  attorney can review mistakes or conclusions.
- **Controlled submissions:** The CLI now has limited visible browser
  assistance for Whitepages and Spokeo. It can initiate Spokeo submission
  only after the user completes its CAPTCHA; email confirmation remains a
  user step. It advances only the first Whitepages step; later steps and
  telephone verification remain manual. This is not ReAct-agent submission
  or end-to-end compliance tracking. For future supported tasks, a clear
  instruction with a named broker authorizes only the minimum ordinary
  information needed by that broker's official process; do not ask for
  redundant per-step confirmation. Tell the user what is being sent. If the
  broker requires unusually sensitive, disproportionate, or unclear
  information (such as a government identifier, account credential, or
  financial data), stop and ask before proceeding. Do not send those details
  to Ollama or public research providers.
- **Independent development:** The feature modules below should be designed
  and developed independently. Cross-module orchestration belongs to the
  concierge; modules retain their own policies, instructions, tools, and
  conclusions.
- **Independent ReAct agents:** Each feature module owns its agent
  configuration, instructions, and tools. A shared framework may provide the
  reusable local model/tool-call loop, but it must not define feature policy
  or coordinate modules. The concierge may call a module-owned agent through a
  narrow, explicitly approved handoff; it must not reproduce that module's
  analysis or pass more data than the user approved. The desktop now supports
  a limited handoff from broker concierge chat to the privacy impact analysis
  specialist. It receives only the current request for general
  education; access to a selected case's local evidence requires separate
  approval. Broader cross-module coordination remains future work.
- **Concierge facade:** The user should be able to state an outcome, such as
  opting out of a broker, and have the future concierge determine the
  documented process, gather only information needed for that process, carry
  out supported steps, and report the outcome. Minimize interruptions; ask
  again only for missing user-specific information, unusually sensitive or
  disproportionate data requests, broker-required consent, or verification.
  Never bypass CAPTCHA, identity checks, access controls, or required human
  steps; automate only interactions permitted by the broker's process.
- **Example material:** The DuckDuckGo Personal Information Removal
  description was shared as an example of public information about broker
  coverage and removal behavior. It is not a requested integration or an
  endorsed source. Any future source or broker record must be evaluated on its
  own merits.

## Module A: Broker compliance, discovery, and opt-out preparation

The current code launches a local desktop app by default and retains a CLI
option. Its application-owned broker directory has two U.S. listing-removal
entries (Whitepages and Spokeo) checked against official sources on 2026-10-22.
The desktop also displays a separate source inventory for reviewed official
California, Oregon, and Texas materials checked on 2026-10-23. Those source
references are not themselves broker records. Clicking **Refresh California
registry** downloads California's public registration CSV and retains a local
snapshot containing only business names, DBAs, and registrant-listed websites.
The registry receives normal connection metadata; the app sends it no personal
data or search query.
Contact details and sensitive-practice disclosures are discarded; candidate
entries are not automatically promoted to the actionable broker directory.
Oregon and Texas rosters are not imported. There is no international source
inventory or global all-sector census yet. The app can display broker
instructions, save local preparation checklists, launch supported browser
assistance, and track local case status, follow-up reminders, and evidence
fingerprints. Case metadata excludes listing URLs, email addresses, evidence
filenames, and evidence contents; local JSON is not encrypted. A visible
Playwright browser helper can enter a user-provided listing URL into Spokeo's
form and initiate submission after user-completed CAPTCHA, or enter a URL and
advance Whitepages' first step. Spokeo's email confirmation and Whitepages'
remaining wizard and telephone verification remain user steps. No result is
independently verified. The directory is not comprehensive and there is no
automated broker discovery from a person's identity. Keep this module focused
on identifying and organizing verified public broker information, carrying
out supported user-directed opt-out tasks through the local app, and tracking
user-provided evidence of the broker's response. The future concierge should
orchestrate these mature module tools.

Make source coverage limits visible whenever users interpret a search result.
Keep the source inventory distinct from the broker directory and from reviewed
opt-out instructions. A no-match result means only that the broker was not
found in the specific sources currently maintained or checked; it does not
establish that no broker exists, that the user is unaffected, or that the
remaining brokers are compliant. Unlisted or opaque brokers warrant additional
scrutiny as a risk-based research priority, but do not describe them as more
likely to act illegally without comparative evidence.

**Future GUI and resource-use directive:** Keep the local desktop application
as the primary interface and add a user-triggered **Search and update broker
list** action. Open a browser only on demand for this bounded search or other
supported broker workflows; do not build an always-on general-purpose crawler.
The Coverage and sources tab now provides a local user-managed source list
where users can inspect, add, edit, and remove entries without waiting for
developers to hardcode them. Saving a source does not fetch it. Next, implement
bounded refresh and comparison using those user-managed sources. Explain each
source's coverage, limitations, and what the app will fetch. Preserve the
concierge facade: the user starts a search, routine bounded fetching and
comparison happen for them, and results are summarized in plain language with
proposed directory changes presented clearly. Avoid repeated technical
prompts, while keeping external requests and the user's authorization of
trusted-directory changes explicit.

Fetch only user-selected public sources in ways permitted by applicable law
and source terms. Add a record to the actionable directory only when evidence
supports both that the organization operates as a data broker and that it has
a current official opt-out process. Store source URLs and last-checked dates,
deduplicate safely, and report skipped or ambiguous candidates instead of
silently promoting them. A search result or registry listing alone is not
proof of broker activity or an actionable opt-out process. Keep discovery
generic and non-identifying; do not search for the user's personal footprint.
Prefer bounded, sequential fetches. Browsers can consume RAM and CPU and may
compete with Ollama for GPU resources; test actual impact on target hardware
rather than promising a fixed performance effect. Keep browser sessions
closed when idle, avoid browser-heavy work concurrent with model generation on
constrained machines, and consider an optional user-controlled Ollama
pause/unload setting only if testing demonstrates value.

The CLI can also fetch one directory-listed official page after explicit
per-page user approval, compare it with the prior local snapshot, and stage a
user-written update for separate approval. This is not scheduled monitoring
or general web search. Fetched text and check history are stored locally
without encryption. The monitor tool is read-only; only the user's explicit
approval can apply an update to the trusted directory. Approved edits are
stored as local overrides, not written into the shipped seed directory.
This page-monitoring capability does not submit opt-out requests or check
whether a broker honored an individual user's request.

For a future case-specific compliance check, distinguish whether the request
was prepared, submitted, acknowledged, answered, and whether the user-provided
or independently reviewed evidence supports the requested outcome. A
published opt-out process, an agent-submitted form, and a broker's actual
handling are separate facts. The agent may report whether documented behavior
appears consistent with the user's request and the evidence; it must not turn
that into an unsupported legal finding.

## Shared ReAct execution framework

`react_framework` is the shared, local execution foundation for module-owned
ReAct agents. It is responsible for communicating with the local Ollama
service, carrying out a bounded tool-call loop, validating tool names and
basic arguments, and returning tool results to the calling module.

Available tool schemas are centrally registered in
`react_framework/tool_catalog.py`. A feature module explicitly binds only the
schemas it needs to its own handler implementations. The framework sends only
that agent's selected tool schemas to Ollama; tools not selected for an agent
are omitted from its prompt. Keep handler behavior in the owning feature
module rather than moving feature logic into the shared framework.

Each module remains responsible for its own agent configuration, system
instructions, allowed tools, tool handlers, and interpretation of results.
The framework must not contain module-specific legal or privacy policy, access
another module's tools, or coordinate work across modules. Evidence-analysis
and repeated-conduct agents have their own configurations and selected
workspace/specialist tools; their domain-specific case tracking and analysis
functionality remains incomplete.

### Concierge chat and future delegation

The desktop keeps its concierge visible beside every tab. It is a local Ollama chat with broker-directory and
discovery tools, a limited approved public broker search through Tavily,
supported broker actions, and a narrowly scoped handoff to the
privacy impact analysis specialist.
Conversation history remains in memory only. From the public-source panel, the
user can ask the app to fetch bounded visible text for discussion; the fetched
text is included only in local Ollama prompts until the user clears it or exits.
It is not persisted or sent to Tavily. The request is limited to a 512 KB
response and 12,000 characters of text, with scripts and embedded content
excluded.
On every chat turn, the assistant also receives bounded visible content from
the selected in-app tab automatically, without an additional consent prompt.
This may include selected broker/source details, a registry candidate, or
selected case metadata; it excludes listing/contact form fields and imported
evidence contents. The context is treated as untrusted data and remains local
to the Ollama request.
This is a first facade, not the complete service: broker coverage is limited,
individual footprint search is disabled, and broad multi-module workflows
remain unimplemented.

As the feature agents and tools mature, expand the chat into a concierge that
understands user goals, selects and calls relevant module-owned agents/tools,
and brings results together to perform supported legwork. This coordination
belongs above the shared ReAct execution framework; it must not move module
policies or handlers into that framework or erase the modules' independent
responsibilities. The privacy impact specialist owns its conclusions; the concierge
conveys them and their stated limits.

The concierge must preserve the project's privacy, evidence, research, and
legal boundaries. Delegation does not authorize sending personal information
to public services, submitting requests, or taking other consequential
external actions without an explicit, appropriately scoped user approval
flow. It must accurately report which agents and tools were used, what they
did, and any limitations or unresolved results.

The shared framework also contains generic case-workspace operations. A case
has an `originals/` folder for explicitly imported copies of source evidence,
a separate `derived/` folder for generated files and copies, and an
`activity.jsonl` log. Agent file tools can read/search originals but cannot
modify, rename, or delete them. Writes and copies are create-new only in
`derived/`. `grep_search` returns exact quotes with case-relative file path,
line number, and SHA-256, and reports files skipped. Current document reading
and search support selected UTF-8 text formats; PDF extraction and scanned
image OCR are not configured.

The central catalog also provides local Ollama specialist invocation schemas
for research planning, architecture review, and preliminary legal
issue-spotting. These are local agent roles, not external delegated services.
The desktop configures its provider-neutral public-search interface with
Tavily, restricted to fixed, generic broker topics and explicit approval of
each exact query. The provider receives the approved query and network
metadata, but not chat history, case files, or user identifiers. Tavily's
technical API documentation was checked; its legal terms, retention practices,
and production-use rights remain unverified. The legal specialist may receive
case context locally but has no verified legal source library.

### Future broker-focused public research

Research may examine where a broker operates or is based; publicly reported
data practices, incidents, investigations, lawsuits, settlements, or other
actions; affected groups or populations described by credible sources; and
possible opt-out, regulator, or attorney-review steps. Do not search for,
collect, or list identified victims' personal information. Distinguish
documented findings from allegations, commentary, and uncertainty, and retain
citations for review.

For future provider expansion, offer only providers whose current terms permit
the planned interface and use. Provider selection does not bypass user
approval: show the exact non-identifying query and provider before sending it.
Do not send case files or victim PII. Explain that the selected provider
receives the query and may handle it under its own policies. Recheck provider
terms and availability; remove or disable a provider if its permitted use
changes.

Agent and tool actions are displayed live. Case-bound activity metadata is
appended locally without recording full prompts or evidence contents.

### Plain-English workflow

1. Maintain a separate inventory of public discovery sources and a broker
   directory. Source presence does not itself verify a broker or its opt-out
   process.
2. Maintain an actionable broker entry only after a person checks the broker's
   current public opt-out process; record provenance, review date, relevant
   jurisdictions, documented method, and actual automation support.
3. When a user asks about a region, search only the maintained verified
   directory.
   Clearly report when there is no matching verified entry. State that the
   directory is incomplete and that no match means "not found in the sources
   checked," not that all brokers have been identified or that the subject is
   compliant.
4. Show the broker's public instructions, source, and verification date. Do
   not let the language model invent a broker, source, URL, legal rule, or
   opt-out procedure.
5. In the current prototype, let the user save a local checklist and complete
   the broker's external form themselves. Do not collect personal details for
   a checklist.
6. In future work, let the user tell the concierge the desired outcome and
   have it determine and carry out the broker's documented opt-out process
   using supported tools. Collect only details required by that broker.
7. A clear instruction to perform an opt-out with a named broker authorizes
   the minimum ordinary information required by that broker's official
   process. Tell the user the destination and fields being sent without
   adding a redundant confirmation step. Pause for consent if the process
   requests unusually sensitive, disproportionate, or unclear information.
   Keep personal details out of model prompts, public searches, and research
   providers.
8. Pause for the user when the broker requires a CAPTCHA, phone call,
   identity verification, additional consent, or another step that cannot or
   must not be automated. Never bypass these controls.
9. Track submission separately from broker acknowledgment, response, and
   verified outcome. Do not claim a request was received, accepted, or
   completed without supporting evidence.
10. Compare later broker conduct with the user's actual request and available
    evidence. State what is supported, user-reported, inferred, or unknown;
    do not make an unsupported legal-compliance finding.
11. Keep a record of source instructions, authorized disclosures, attempted
    action, broker response, outcome evidence, and remaining uncertainties.
12. Prioritize opaque and unlisted broker leads for careful public-record
    research as a risk-management choice. Distinguish that priority from
    proof or a statistically supported claim that such brokers are more
    likely to violate laws.

### Open questions for later

- What source-maintenance and re-verification process should establish that a
  broker listing remains current?
- How should people contribute corrections, and who reviews them?
- Which region and jurisdiction labels should be supported first?
- Should this module eventually support user-led searches on broker sites?
  This is not permission to send a person's identifying information to such a
  site; that privacy question must be addressed explicitly first.

## Module B: Evidence, possible impacts, legal research, and attorney preparation

The concept in `agent_ollama_data_mishandling_damages_expert/todo` is a
standalone case-analysis area. Its role is to help the user assemble facts,
understand possible impacts, conduct public-source research, and prepare
material for a professional attorney. A basic local evidence workspace and
agent configuration now exist, with a user-reported case timeline in the
desktop. Full case management, PDF/OCR, live legal research, and legal-source
analysis remain future work.

### Plain-English workflow

1. Let the user create a case record stored locally by the application.
2. Let the user add evidence such as dated screenshots, notices, broker
   correspondence, opt-out receipts, user-written letters and proof of
   delivery, PDFs, scanned images, records about consent or agreements, and a
   description of effects the user experienced.
3. Preserve each original item as supplied. Record basic context the user
   provides, such as when it was created or received, who sent or received it,
   and what event it relates to. Do not silently change the original.
4. If text is extracted from a scan or image, preserve it as a separate,
   machine-produced derivative. Mark uncertain extraction for user review and
   keep the original available for comparison.
5. Build a chronological view from evidence and user-entered dates. The current
   timeline records user-reported event types and date bases, links imported
   originals by case-relative path and SHA-256, and sorts unknown dates last.
   Evidence links may include user-described source, sender, recipient, date,
   and event relationship. Corrections are appended and linked, not substituted.
   A fingerprint is not proof of authenticity or event truth.
6. Ask the local ReAct agent to analyze the selected case material only after
   the user starts that analysis. The desktop now provides a direct,
   separately approved case-timeline action for the impact specialist. Keep
   its displayed conclusions separate from original evidence and do not
   persist them without a separate user choice.
7. For legal or factual research, use public sources and non-identifying
   queries only. Never put the user's name, email, address, case details, or
   other personal identifiers into an online query.
8. When the broker's location or jurisdiction is known, investigate relevant
   public legal sources for that jurisdiction, and separately identify any
   applicable user jurisdiction. If location or applicability is unclear,
   report that uncertainty rather than guessing.
   Never assume that the jurisdiction with the strongest protections governs
   the user. A user-requested benchmark is for comparison only; if local
   protections are not established, state that limitation and offer a
   user-reviewed educational summary or questions for local lawmakers, not
   direct contact.
9. For each research-based statement, show the source, the portion relied on,
   when it was accessed, and how the agent connects it to the recorded facts.
   Separate quoted/source facts from the agent's interpretation.
10. Describe possible impacts from the evidence and the user's account. The
    direct impact-expert review is available from the case timeline.
    Identify missing evidence, alternative explanations, and uncertainties.
    Do not invent events, present an allegation as established fact, or state
    that a legal violation or compensable amount is proven merely because the
    agent found it plausible.
11. Help the user prepare an organized attorney-review package: a factual
    timeline, an evidence index, relevant public sources, questions to ask,
    and clearly labeled preliminary analysis. The current previewable draft
    includes the user-reported timeline, up to 100 imported-file metadata
    entries, user-provided questions, and limits; it excludes original file
    contents, legal research, and agent conclusions.
12. Let the user review the exact draft and explicitly approve saving a new
    local Markdown derivative. The draft is not transmitted or shared.

### Open questions for later

- Which jurisdictions and authoritative public legal sources should be
  supported first?
- What local case-file format, backup behavior, retention controls, and
  deletion/export process should be used?
- Which document types and extraction methods should be supported first?
- What should an attorney-review summary include, and what should remain
  private unless the user deliberately selects it?
- Is any monetary damages discussion desired, and if so, what evidence and
  qualifications are required? Do not assume the agent can establish a
  damages amount.

## Module C: Repeated broker conduct after notice

The concept in `repeated_broker_conduct_tracker/todo` is a standalone
tracking area for cases where a user has appropriately asked a broker to stop
or remove data, but later observes continued or repeated activity. Its own
agent configuration can use the local evidence workspace; event tracking and
domain-specific behavior remain future work.

### Plain-English workflow

1. Let the user record a notice sent to a broker, including the notice text or
   copy, recipient, date, delivery method, and any proof of sending or receipt.
2. Let the user record each later observation separately, including when and
   how it was observed and any supporting screenshot, letter, report, or other
   evidence.
3. Link an observation to a prior notice only when the user or a later review
   establishes why they believe it concerns the same broker and information.
4. Keep the distinction between confirmed delivery, broker response, user
   observation, and agent inference visible in the record.
5. Present events in date order and flag gaps, conflicting dates, or missing
   supporting evidence for the user to review.
6. Let the local agent research public information about the broker and
   relevant jurisdictions using non-identifying queries. Attach sources and
   access dates to research notes.
7. Let the agent explain possible administrative next steps or questions for
   an attorney based on the recorded timeline and researched sources.
8. Do not automatically label repeated activity unlawful or deliberate.
   Present the evidence and reasoning so the user and attorney can evaluate it.
9. Keep any attorney-review summary as a clearly labeled derivative of the
   original event records and evidence.

### Open questions for later

- What kinds of user action count as a notice for purposes of this tracker?
- How should the app represent a broker's partial response, disputed identity,
  reopened listing, or an observation that may come from a different source?
- What amount of evidence should be required before a timeline labels an
  event as confirmed rather than user-reported?

## Development sequence

This is a suggested order for discussion, not authorization to begin coding:

1. Keep the reusable local ReAct execution framework focused on local Ollama
   communication, bounded tool calls, and validation of tool requests and
   results.
2. Keep each feature module's agent configuration, instructions, and
   independent tool registry in that module, importing only the shared
   execution framework.
3. Clarify the expected user experience and minimum record-keeping needs for
   each independent module.
4. Agree on the evidence and source distinctions that every module must
   preserve.
5. Develop each module independently, with its own purpose and workflow.
6. Review the privacy, research, and legal-jurisdiction boundaries as each
   module is specified.
7. After the modules and their tools are sufficiently developed, specify the
   delegating concierge's responsibilities, handoffs, user-approval points,
   and reporting behavior. Keep orchestration separate from the shared ReAct
   execution framework and preserve each module's independent policies and
   tools.
